# Memory Compilers: SRAM, Register Files, and ROM Generators

## Overview

Memory dominates the area of modern SoCs, often comprising 50-70% of the total die area. Unlike logic, which is built from standard cells placed by the PnR tool, memory arrays are generated by memory compilers -- parameterized generators that produce optimized memory blocks (macros) tailored to specific requirements. Physical design engineers must understand memory compiler options, the impact of configuration choices on area/timing/power, and how to integrate generated memories into the physical design flow.

## SRAM Compilers

### Fundamentals

SRAM (Static Random Access Memory) compilers generate custom SRAM arrays with user-specified word depth, bit width, and configuration options. The compiler produces all necessary views:

- **GDS/OASIS**: Physical layout for manufacturing
- **LEF**: Abstract view for place-and-route (pin locations, blockages, size)
- **Liberty (.lib)**: Timing and power models for multiple PVT corners
- **Verilog**: Behavioral/functional model for simulation
- **SPICE netlist**: For analog/circuit simulation
- **CDL**: For LVS verification

### SRAM Bit-Cell

The core of any SRAM is the bit-cell. The classic 6T SRAM cell uses 6 transistors (2 cross-coupled inverters + 2 access transistors). Key parameters:

- **Cell area**: Ranges from 0.021 um^2 (N5) to 0.370 um^2 (28nm). Bit-cell size directly determines SRAM density
- **Read/write stability**: Measured by SNM (static noise margin). Larger cells have better stability
- **Leakage per bit**: Determines total SRAM leakage, which can dominate chip leakage

Some compilers offer high-density (HD) and high-performance (HS/HP) bit-cell variants:
- HD cells are smaller but slower and less stable
- HP cells are larger but faster with better noise margins

### Configuration Parameters

When generating an SRAM macro, the following parameters must be specified:

#### Word Depth and Bit Width

- **Words**: Number of addressable locations (e.g., 256, 512, 1024, 4096)
- **Bits**: Width of each word (e.g., 8, 16, 32, 64, 128)
- Total capacity = Words x Bits

#### Mux Ratio (Column Multiplexing)

The mux ratio determines how many bit-cell columns share a single sense amplifier and write driver:

- **Mux 2**: Every 2 columns share one I/O. Wider array, shorter bit-lines
- **Mux 4**: Every 4 columns share one I/O. Standard balance of width vs. height
- **Mux 8**: Every 8 columns share one I/O. Taller array, narrower footprint
- **Mux 16**: Maximum column sharing. Tallest, narrowest configuration

Mux ratio impacts:
- **Aspect ratio**: Higher mux = taller/narrower macro. Lower mux = shorter/wider
- **Speed**: Higher mux generally slower (longer word-line, more column decode)
- **Power**: Higher mux can reduce dynamic power (fewer bit-lines toggling per access)
- **Area**: Mux 4 is often the area-optimal choice

#### Aspect Ratio Selection

Choosing the right aspect ratio is critical for floorplanning:
- Macro dimensions must fit into the available floorplan space
- Pin locations (address, data, control on specific edges) must be accessible for routing
- Avoid extreme aspect ratios (>4:1) that create routing congestion

#### Banks

Large memories can be split into banks:
- Each bank operates independently with separate decoders
- Banking reduces active power (only one bank is accessed per cycle)
- Multi-bank configuration adds area overhead but improves power and timing

### Power Modes

Modern SRAM compilers support multiple power modes:

- **Active mode**: Normal read/write operation
- **Light sleep**: Peripheral circuits powered down; bit-cell array retains data. Reduced leakage (~50% reduction), fast wake-up (~1-5 cycles)
- **Deep sleep**: Further power reduction with slower wake-up. Bit-cells use minimum retention voltage
- **Shutdown**: Complete power-off. Data is lost. Maximum leakage savings
- **Retention (power gating)**: External retention voltage maintains bit-cell state while primary supply is gated

Power mode pins are additional control signals that must be connected in the design and managed by the power controller.

## Register File Compilers

Register files are multi-ported memories optimized for simultaneous read and write access, commonly used in processor register files, scoreboards, and FIFOs.

### Key Differences from SRAM

- **Multi-port**: Typically 2-read/1-write (2R1W), 1-read/1-write (1R1W), or even 6R2W
- **Bit-cell size**: Multi-port cells are larger than 6T SRAM (8T for 1R1W, 10T for 2R1W)
- **Speed**: Optimized for single-cycle access at high frequency
- **Size**: Typically smaller capacities than SRAM (8-128 entries)

### Register File Configuration

- Word depth: 8 to 128 entries (typical)
- Bit width: 8 to 128 bits
- Port configuration: read ports, write ports, read/write ports
- Some compilers offer register file macros with bypass logic (write-through)

### Area and Timing Impact

- 2R1W register file is ~2x the area of equivalent 1R1W SRAM
- Register files have faster access times than SRAM due to shorter word-lines
- Multi-port architectures increase routing complexity around the macro

## ROM Generators

ROM (Read-Only Memory) generators create memory arrays that store fixed data programmed during manufacturing:

### Types

- **Mask ROM**: Data is defined by the metal pattern. One-time programmable at tapeout
- **Via ROM**: Data is encoded in via presence/absence. More flexible for late-stage ECOs
- **Flash-based**: Electrically programmable but much larger bit-cells

### Configuration

- Word depth and bit width
- Programming data (binary content file)
- Typically single-port, single-read

### Advantages

- Very high density (ROM bit-cells can be 50-70% smaller than SRAM)
- Zero leakage (no active transistors holding state)
- Used for boot code, lookup tables, calibration data, security keys

## Characterization

Memory compilers generate Liberty models characterized at multiple corners:

### PVT Corners

Standard corners include:
- **SS (slow-slow)**: Worst-case setup timing
- **FF (fast-fast)**: Worst-case hold timing
- **TT (typical-typical)**: Nominal performance
- Temperature: -40C, 25C, 85C, 125C
- Voltage: nominal +/- 10%

### Timing Parameters

- **Access time**: Clock-to-Q delay for read operations
- **Cycle time**: Minimum clock period
- **Setup/hold time**: Data and address input requirements relative to clock
- **Write pulse width**: Minimum clock high period for write
- **Output enable time**: For memories with output enable control

### Power Characterization

- Dynamic power per read/write operation (at specified frequency and toggle rate)
- Leakage power per mode (active, sleep, retention, shutdown)
- Clock power (internal clock tree within the memory)

## Integration into Physical Design

### Floorplanning

- Place memories early during floorplanning
- Consider pin orientation: data pins face the core logic, power pins face the ring
- Allow adequate halo/blockage around memories for routing and power connections
- Group related memories to minimize interconnect

### Timing Integration

- Import Liberty models for all required PVT corners
- Memory access time is often on the critical path; consider it early in timing budgeting
- Add margin for memory timing variation (foundry-provided derating)

### Power Integration

- Connect memory power modes to the system power controller
- Verify retention voltage levels during power gating
- Include memory leakage in total power estimation

### Physical Verification

- Memory GDS must be merged for final DRC/LVS
- Memory block may have special DRC waivers (allowed by foundry)
- Verify memory antenna rules are met at the block boundary

## Practical Guidance

1. **Generate early, iterate as needed**: Generate initial memories early for floorplanning. Regenerate if aspect ratio needs change
2. **Minimize memory instances**: Consolidate small memories where possible to reduce overhead (decoder, periphery share)
3. **Mux 4 as starting point**: Mux 4 is typically the best area/timing/power tradeoff. Only change if aspect ratio or timing dictates
4. **Test infrastructure**: Ensure BIST (Built-In Self-Test) or scan access is planned for every memory instance
5. **Track compiler versions**: Memory compiler versions must match the PDK version. Mismatches cause DRC/LVS failures
6. **Power mode verification**: Verify all memory power mode sequences in simulation before committing to the implementation
