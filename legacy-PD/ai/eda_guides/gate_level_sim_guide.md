# Gate-Level Simulation (GLS) Complete Guide

Comprehensive guide for setting up and running gate-level simulations with
SDF timing annotation, X-propagation analysis, timing violation debug,
power-aware GLS, performance optimization, and regression strategies.

---

## 1. GLS Overview

### 1.1 Purpose of Gate-Level Simulation

Gate-level simulation (GLS) verifies the design at the netlist level (after
synthesis or place-and-route) to catch issues that are invisible at RTL:

| Issue Type | Description | RTL Visible? |
|-----------|-------------|-------------|
| Timing violations | Setup/hold/pulse width violations | No |
| X-propagation | Unknown values from uninitialized or violated logic | No |
| Glitches | Combinational glitches on clock/reset paths | No |
| Clock gating | Incorrect clock gating cell insertion | Partially |
| Scan chain | DFT insertion effects on functional mode | No |
| Power domain | Isolation/retention cell behavior | With UPF only |
| Synthesis artifacts | Logic optimization side effects | No |
| STA exceptions | False/multi-cycle path validation | No |

### 1.2 GLS Flow

```
RTL Simulation (functional verification)
        |
        v
Synthesis Netlist + SDF (post-synth GLS)
        |
        v
Place & Route Netlist + SDF (post-PnR GLS)
        |
        v
Sign-off Netlist + SDF (final GLS)
```

### 1.3 Types of GLS

| Type | Netlist | SDF | Purpose |
|------|---------|-----|---------|
| Zero-delay GLS | Post-synth | None | Functional equivalence with gates |
| Unit-delay GLS | Post-synth | Unit | Basic timing path validation |
| Post-synth SDF GLS | Post-synth | Synth SDF | Synthesis timing check |
| Post-PnR SDF GLS | Post-PnR | PnR SDF | Final timing verification |
| Post-PnR max GLS | Post-PnR | Max SDF | Worst-case (setup) check |
| Post-PnR min GLS | Post-PnR | Min SDF | Best-case (hold) check |
| Back-annotated GLS | Post-PnR | Full SDF | Complete timing annotation |

## 2. GLS Setup

### 2.1 Required Files

```
GLS Setup Files:
  1. Gate-level netlist (.v or .sv)
     - Post-synthesis or post-PnR Verilog netlist
     - Includes standard cell instances

  2. SDF file (.sdf)
     - Standard Delay Format timing annotation
     - Contains cell delays, interconnect delays
     - Generated by synthesis or PnR tool

  3. Standard cell libraries (.v)
     - Behavioral Verilog models of standard cells
     - Timing-annotatable (with specify blocks)
     - Multiple corners (typical, fast, slow)

  4. Technology libraries
     - Verilog simulation models for memories, IPs
     - Typically from foundry or IP vendor

  5. Testbench
     - Same testbench as RTL (with minor modifications)
     - Clock/reset generation
     - Interface connections (may need rewiring for netlist ports)
```

### 2.2 Compilation

**VCS (Synopsys):**

```bash
vcs -full64 -sverilog \
    -debug_access+all \
    +neg_tchk \
    +notimingcheck \
    +nospecify \
    +delay_mode_zero \
    -v /path/to/std_cell_library.v \
    -v /path/to/memory_models.v \
    -v /path/to/io_models.v \
    -f design_netlist.f \
    -f testbench.f \
    -top tb_top \
    -o simv_gls \
    -l compile_gls.log

# With timing annotation (full GLS)
vcs -full64 -sverilog \
    -debug_access+all \
    +neg_tchk \
    +sdfverbose \
    -sdf max:tb_top.dut:timing_max.sdf \
    -v /path/to/std_cell_library.v \
    -v /path/to/memory_models.v \
    -f design_netlist.f \
    -f testbench.f \
    -top tb_top \
    -o simv_gls \
    -l compile_gls.log

# VCS timing-related switches
# +neg_tchk        : Enable negative timing checks
# +notimingcheck   : Disable all timing checks (zero-delay GLS)
# +nospecify        : Ignore specify blocks (zero-delay GLS)
# +delay_mode_zero  : Force all delays to zero
# +delay_mode_unit  : Force all delays to unit (1 time unit)
# +sdfverbose       : Verbose SDF annotation messages
# +overlap          : Allow overlapping timing check windows
# +multisource_int_delays : Handle multi-source interconnect delays
# -negdelay         : Allow negative delays in SDF
```

**Xcelium (Cadence):**

## 3. SDF Annotation

### 3.1 SDF File Structure

```sdf
(DELAYFILE
  (SDFVERSION "4.0")
  (DESIGN "my_design")
  (DATE "2024-01-15")
  (VENDOR "my_foundry")
  (PROGRAM "my_pnr_tool")
  (VERSION "1.0")
  (DIVIDER /)
  (VOLTAGE 0.900::0.900)
  (PROCESS "1.000::1.000")
  (TEMPERATURE 125.000::125.000)
  (TIMESCALE 1ns)

  (CELL
    (CELLTYPE "NAND2X1")
    (INSTANCE u_ctrl/U123)
    (DELAY
      (ABSOLUTE
        (IOPATH A Y (0.050:0.065:0.080) (0.040:0.055:0.070))
        (IOPATH B Y (0.055:0.070:0.085) (0.045:0.060:0.075))
      )
    )
    (TIMINGCHECK
      (SETUP (posedge D) (posedge CK) (0.030:0.040:0.050))
      (HOLD  (posedge D) (posedge CK) (0.010:0.015:0.020))
      (SETUP (negedge D) (posedge CK) (0.035:0.045:0.055))
      (HOLD  (negedge D) (posedge CK) (0.012:0.017:0.022))
    )
  )

  (CELL
    (CELLTYPE "BUFX4")
    (INSTANCE u_ctrl/U456)
    (DELAY
      (ABSOLUTE
        (IOPATH A Y (0.020:0.025:0.030) (0.018:0.023:0.028))
      )
    )
  )

  // Interconnect delays
  (CELL
    (CELLTYPE "my_design")
    (INSTANCE)
    (DELAY
      (ABSOLUTE
        (INTERCONNECT u_ctrl/U123/Y u_ctrl/U456/A
          (0.010:0.015:0.020) (0.010:0.015:0.020))
      )
    )
  )
)
```

### 3.2 SDF Annotation Options

```
SDF Delay Selection (MTM):
  MINIMUM   : Use min delay values (best case, hold checking)
  TYPICAL   : Use typical delay values
  MAXIMUM   : Use max delay values (worst case, setup checking)

Annotation Order:
  1. Cell delays (IOPATH)
  2. Interconnect delays (INTERCONNECT)
  3. Timing checks (SETUP, HOLD, RECOVERY, REMOVAL, WIDTH, PERIOD, SKEW)

Scale Factors:
  (min_factor : typ_factor : max_factor)
  Default: 1.0:1.0:1.0
  Can scale delays for sensitivity analysis
```

## 4. X-Propagation

### 4.1 Sources of X in GLS

| Source | Description | Severity |
|--------|-------------|----------|
| Uninitialized flops | Registers not reset | High |
| Timing violations | Setup/hold violations cause X | High |
| Bus contention | Multiple drivers on same net | High |
| Floating inputs | Unconnected inputs | Medium |
| Power domain | Signals from powered-off domain | Medium |
| Scan chain | Scan signals in functional mode | Low |
| Memory uninitialized | Memory content before write | Low |

### 4.2 X-Optimism vs X-Pessimism

```
X-Optimism (default in most simulators):
  - MUX with X select may resolve to a value if both inputs are same
  - if (X) evaluates to false in simulation
  - Result: Bugs may be HIDDEN because X is resolved optimistically
  - Risk: Design appears to work but has real X issues

X-Pessimism:
  - Any X on any input propagates X to output
  - if (X) propagates X
  - Result: More X values than reality
  - Risk: False failures, but no hidden bugs

Example:
  MUX: sel=X, a=1, b=1 -> out = ?
    X-Optimism: out = 1 (both inputs same, X doesn't matter)
    X-Pessimism: out = X (select is unknown)

  MUX: sel=X, a=1, b=0 -> out = ?
    X-Optimism: out = X (inputs differ, result unknown)
    X-Pessimism: out = X (select is unknown)
```

### 4.3 X-Propagation Settings

**VCS X-Propagation:**

```bash
# Enable X-propagation mode (VCS)
vcs -xprop=tmerge          # T-merge: X on select -> merge inputs
vcs -xprop=xmerge          # X-merge: X on select -> X output
vcs -xprop=vmerge          # V-merge: custom per-module

# X-propagation configuration file
vcs -xprop=xprop.cfg

# xprop.cfg:
# module cpu_core xmerge;      # Strict X for CPU
# module fifo_ctrl tmerge;     # T-merge for FIFO
# module clock_gen off;        # No xprop for clock gen

# VCS X-handling switches
vcs +xzcheck                  # Check for X/Z on control signals
vcs -xzcheck                  # Disable X/Z checking
```

**Xcelium X-Propagation:**

```bash
# Enable X-propagation (Xcelium)
xrun -xprop m                 # Merge mode
xrun -xprop f                 # Forward-only mode
xrun -xprop c                 # Complete mode (most pessimistic)

# X-propagation configuration
xrun -xprop_config xprop.cfg

# xprop.cfg:
# set xpropMode -module cpu_core -mode complete
# set xpropMode -module fifo -mode merge
```

**Questa X-Propagation:**

```bash
# Enable X-propagation (Questa)
vsim -xprop

# Configuration
vsim -xprop=xprop.cfg
```

### 4.4 Debugging X Issues

```
X Debug Methodology:
====================

1. Identify X source
   - Open waveform
   - Trace X backward through logic cone
   - Find the first flip-flop or primary input with X

2. Categorize X source
   a. Uninitialized register:
      - Verify reset assertion covers this register
      - Check reset connectivity
      - Add initialization or fix reset logic

   b. Timing violation:
      - Check SDF annotation for the failing cell
      - Verify clock tree and data path timing
      - Cross-reference with STA reports

   c. Bus contention:
      - Check for multiple drivers
      - Verify tri-state enable logic
      - Check isolation cell enable timing

   d. Cross-domain:
      - Check synchronizer presence
      - Verify CDC path timing

3. Fix and verify
   - Apply RTL fix (if design bug)
   - Re-run GLS with same test/seed
   - Verify X is resolved
```

### 4.5 X-Filtering and Suppression

```systemverilog
// Suppress known X during initialization
`ifdef GLS
  initial begin
    // Allow X during reset
    force dut.data_valid = 0;
    @(posedge rst_n);
    repeat(50) @(posedge clk);
    release dut.data_valid;
  end

  // Filter X on known uninitialized memories
  initial begin
    // Pre-initialize memories (if no hardware init)
    $readmemh("init_data.hex", tb_top.dut.u_mem.mem_array);
  end
`endif

// X-aware comparison in scoreboard
function bit compare_with_x(logic [31:0] actual, logic [31:0] expected);
  // Mask bits that are X in expected
  logic [31:0] mask;
  for (int i = 0; i < 32; i++) begin
    mask[i] = (expected[i] !== 1'bx);
  end
  return ((actual & mask) === (expected & mask));
endfunction
```

## 5. Timing Violations

### 5.1 Timing Check Types

| Check | Description | Violation Effect |
|-------|-------------|-----------------|
| Setup | Data must be stable before clock edge | X on output |
| Hold | Data must be stable after clock edge | X on output |
| Recovery | Async signal stable before clock edge | X on output |
| Removal | Async signal stable after clock edge | X on output |
| Pulse Width | Minimum pulse width of clock/signal | X on output |
| Period | Minimum clock period | X on output |
| Skew | Maximum skew between signals | Warning |

### 5.2 Setup Time Violations

```
Setup violation occurs when data changes too close to the clock edge:

        Data change
            |
     -------|-----+
            |     |
     tsetup |     |
     <----->|     |
            |     |
    --------+-----+------  Clock edge
            |
     Violation window

Effect: Register may capture incorrect value -> X in simulation
Fix: Add pipeline stage, optimize data path, adjust clock
```

### 5.3 Hold Time Violations

```
Hold violation occurs when data changes too soon after the clock edge:

    Clock edge
        |
    ----+-----+
        |     |
        | thold
        |<--->|
        |     |
    ----+-----+--------  Data must be stable
        |
     Violation window

Effect: Register may capture incorrect value -> X in simulation
Fix: Add buffer delay, adjust clock tree, add hold fix cells
```

### 5.4 Timing Violation Messages

```
VCS timing violation messages:
  "Timing violation in <instance>"
  "Setup Check : <value> : data : <data_edge> : clock : <clock_edge>"
  "Hold Check : <value> : data : <data_edge> : clock : <clock_edge>"
  "Recovery Check : ..."
  "Removal Check : ..."
  "Width Check : ..."

Example:
  Warning: Timing violation in tb.dut.u_ctrl.reg_q
    Setup Check : 0.050 : data : posedge : clock : posedge
    Expected: 0.060ns  Got: 0.045ns (violation of 0.015ns)
    at time 1234.567ns

Xcelium:
  ncsim: *W,TCHECK: ... Setup violation ...
  ncsim: *W,TCHECK: ... Hold violation ...
```

### 5.5 Handling Timing Violations

```bash
# Suppress timing violations selectively (for debug, not sign-off)
# VCS:
vcs +notimingcheck              # Disable ALL timing checks
vcs +no_tchk_msg                # Suppress timing check messages
vcs +no_notifier                # Disable notifier (no X on violation)

# Suppress specific violation types
# In Verilog specify block:
# $setup(..., notifier);  // notifier toggles on violation -> X
# To suppress: disable the notifier

# Count violations
# VCS:
+lint=TFIPC-L                  # Report timing violations as lint

# Log violations to file
vcs +timing_violation_log=violations.log
```

### 5.6 Timing Violation Analysis

```
Timing Violation Analysis Flow:
1. Collect all timing violations from GLS log
2. Categorize:
   a. Setup violations -> Check STA slow corner
   b. Hold violations -> Check STA fast corner
   c. Pulse width -> Check clock generation
3. Cross-reference with STA:
   - Is this path constrained?
   - Is there a false/multi-cycle path?
   - Is the timing met in STA?
4. For real violations:
   - File timing bug
   - Check ECO options
   - Re-run PnR/CTS if needed
5. For false violations:
   - Document and add to GLS waiver list
   - Verify STA constraints cover this path
```

```bash
# Power-aware specific checks

# - Corruption semantics for power-off
# - Isolation enable timing vs power switch timing
# - Retention save/restore protocol
```

### 6.2 Power State Verification in GLS

```systemverilog
// Power state assertions for GLS
`ifdef GLS
module power_gls_checker(
  input logic clk,
  input logic rst_n,
  input logic power_switch_ack,
  input logic iso_enable,
  input logic ret_save,
  input logic ret_restore
);

  // Isolation must be enabled before power off
  a_iso_before_poweroff: assert property (
    @(posedge clk) disable iff (!rst_n)
    $fell(power_switch_ack) |-> $past(iso_enable, 2)
  ) else $error("Isolation not enabled before power off");

  // Retention save before power off
  a_save_before_off: assert property (
    @(posedge clk) disable iff (!rst_n)
    $fell(power_switch_ack) |-> $past(ret_save)
  ) else $error("Retention save not asserted before power off");

  // Retention restore after power on
  a_restore_after_on: assert property (
    @(posedge clk) disable iff (!rst_n)
    $rose(power_switch_ack) |-> ##[1:10] ret_restore
  ) else $error("Retention restore not asserted after power on");

endmodule
`endif
```

## 7. GLS Performance Optimization

### 7.1 Simulation Speed

Gate-level simulation is typically 10x-100x slower than RTL simulation.

| Technique | Speedup | Description |
|-----------|---------|-------------|
| Zero-delay GLS | 5-10x vs SDF GLS | No timing annotation |
| Selective annotation | 2-5x | Only annotate critical blocks |
| Region-based annotation | 2-3x | Annotate specific regions |
| Event reduction | 2-4x | Reduce toggle activity |
| Two-state simulation | 1.5-2x | Disable X propagation |
| Parallel simulation | 2-8x | Multi-core simulation |
| Partitioning | 2-4x | Partition into sub-blocks |

### 7.2 Selective SDF Annotation

```bash
# Annotate only specific blocks
# VCS:
vcs -sdf max:tb_top.dut.cpu_core:cpu_timing.sdf \
    -sdf max:tb_top.dut.bus_if:bus_timing.sdf
# Other blocks use zero delay

# Xcelium:
# In sdf_cmd.tcl:
# SDF_FILE = "cpu_timing.sdf",
# SCOPE = tb_top.dut.cpu_core;
#
# SDF_FILE = "bus_timing.sdf",
# SCOPE = tb_top.dut.bus_if;
```

### 7.3 Parallel Simulation

```bash
# VCS parallel simulation
vcs -full64 -j8 ... # 8-thread compilation

# Partitioned simulation
# Divide chip into regions for independent GLS runs
# Run block-level GLS in parallel
```

## 8. Debug: RTL vs GLS Comparison

### 8.1 Waveform Comparison

```
RTL vs GLS Comparison Methodology:
1. Run same test on both RTL and GLS
2. Dump waveforms from both
3. Compare key signals:
   - Clock
   - Reset
   - Primary inputs/outputs
   - Internal state machines
   - Data paths
4. Identify first divergence point
5. Trace backward to find root cause
```

### 8.2 Signal Mapping

```systemverilog
// RTL signal names may differ from netlist
// Create mapping file or signals file

// RTL:  dut.cpu.alu.result[31:0]
// GLS:  dut.cpu.alu.\result_reg[31] , ..., dut.cpu.alu.\result_reg[0]

// Use hierarchical references carefully
// RTL:  dut.ctrl.state == IDLE
// GLS:  dut.ctrl.\state_reg[2:0] == 3'b000
```

### 8.3 Mismatch Debug Flow

```
GLS Mismatch Debug:
1. Identify failing output
2. Compare RTL and GLS waveforms
3. Find first cycle of divergence
4. Check for timing violations at that time
5. Check for X propagation
6. Trace back to source:
   a. If timing violation -> check STA
   b. If X from reset -> check reset path
   c. If functional difference -> check synthesis
   d. If X from power domain -> check UPF
7. Apply fix and re-run
```

### 8.4 Common GLS Issues and Solutions

| Issue | Symptom | Root Cause | Solution |
|-------|---------|-----------|----------|
| Output X after reset | X on ports after reset release | Incomplete reset | Fix reset logic |
| Intermittent X | Random X on data | Timing violation | Fix timing or STA constraint |
| Stuck output | Output never changes | Clock gating issue | Check clock tree |
| Wrong data | Output differs from RTL | Synthesis optimization | Review synthesis constraints |
| Deadlock | Design hangs | X on control signal | Trace X to source |
| Memory corruption | Wrong memory content | SDF on memory | Check memory model |
| Scan interference | Functional mode failure | Scan not disabled | Verify scan_enable=0 |

## 9. GLS Regression Strategy

### 9.1 Test Selection for GLS

Not all RTL tests need to run at gate level. Select tests based on:

| Priority | Test Type | Rationale |
|----------|-----------|-----------|
| P0 | Reset and initialization | Verify reset path at gate level |

### 9.2 GLS Regression Configuration

```
GLS Regression Tiers:

Tier 1 - Sanity (run daily):
  - 5-10 basic tests
  - Zero-delay GLS
  - ~30 minutes
  - Catches: synthesis bugs, connectivity issues

Tier 2 - Standard (run nightly):
  - 50-100 selected tests
  - Post-PnR SDF GLS (max delays)
  - 4-8 hours
  - Catches: timing violations, X issues

Tier 3 - Full (run weekly):
  - 200+ tests
  - Both max and min SDF
  - 24-48 hours
  - Catches: hold violations, corner cases

Tier 4 - Sign-off (run before tapeout):
  - All GLS-compatible tests
  - All corners
  - Power-aware GLS
  - Multiple days
```

### 9.3 GLS Pass/Fail Criteria

```
GLS Pass Criteria:
  1. No X on primary outputs (after reset stabilization)
  2. All functional checks pass (same as RTL)
  3. No timing violations in critical paths
  4. No bus contention
  5. No unknown states in FSMs

GLS Waiver Criteria:
  1. Timing violations on STA-waived paths (false/multi-cycle)
  2. X on test-mode-only signals
  3. X on debug-only ports
  4. Known memory initialization X (pre-first-write)

GLS Failure Investigation:
  1. New failure vs known failure
  2. Cross-reference with STA report
  3. Compare with RTL result (same test/seed)
  4. Classify: timing / functional / infrastructure
```
