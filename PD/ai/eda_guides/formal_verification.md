# Formal Verification (Equivalence Checking)

## Overview

Formal verification mathematically proves that two representations of a design are functionally equivalent without requiring simulation vectors. In the physical design flow, Logic Equivalence Checking (LEC) is performed at multiple stages to verify that transformations (synthesis, scan insertion, PnR optimization, ECO) did not alter the design's functionality. Unlike simulation, formal verification is exhaustive — it checks all possible input combinations.

## Why Formal Verification Is Essential

Every stage of the physical design flow modifies the netlist:

- **Synthesis:** Transforms RTL to gates — logic restructuring, cell mapping, optimization
- **Scan insertion:** Adds scan chains, mux structures, test logic
- **Placement optimization:** Buffer insertion, cell sizing, Vt swapping
- **CTS:** Clock buffer insertion, clock gate restructuring
- **Routing optimization:** Post-route buffer insertion, gate sizing
- **ECO:** Functional or timing fixes that modify gates

Each transformation must preserve the design's logical behavior. Formal verification catches bugs that simulation might miss because it checks all possible states, not just simulated scenarios.

## LEC Concepts

### Reference vs. Implementation

- **Reference (golden):** The trusted design representation. Starts as RTL and updates as the flow progresses.
- **Implementation (revised):** The design representation being verified against the reference.

### Comparison Points

LEC identifies corresponding sequential elements (flip-flops, latches) between reference and implementation, then proves that the combinational logic between them is equivalent.

**Key point types:**

- **DFF (D flip-flop):** Rising or falling edge-triggered register
- **DLAT (D latch):** Level-sensitive latch
- **BBOX (black box):** Unverifiable element (e.g., analog block, memory)
- **Primary input/output:** Top-level ports

### Equivalence States

| Status | Meaning |
|--------|---------|
| Equivalent | Mathematically proven identical |
| Non-equivalent | Proven different — a real bug |
| Abort | Tool could not prove or disprove (complexity limit reached) |
| Not compared | Points not mapped between reference and implementation |


### SVF (Setup Verification Guidance)

The SVF file is generated by the synthesis tool (DC, FC, Genus) and records all transformations applied during synthesis. Formality uses SVF to understand how the design was modified and guide the verification process.

**Why SVF is critical:**

- Register retiming changes the sequential boundaries — without SVF, LEC cannot match retimed registers.
- Multibit banking merges multiple flip-flops into a single cell.
- Clock gating insertion adds new sequential elements.
- Boundary optimization changes interface logic.

```tcl
# In DC/FC: enable SVF generation
set_svf my_design.svf

# In Formality: read SVF
set_svf my_design.svf
```

**Without SVF, LEC failure rate increases dramatically.** Always generate and use SVF.

## Handling Special Cases

### Clock Gating Verification

Clock gating introduces new logic in the clock path. LEC must handle the enable/clock relationship correctly.

```tcl
# In Formality
set_constant scan_enable 0     ;# Disable test mode
set_constant scan_mode 0

# Formality auto-detects ICG cells with SVF
```

### Register Retiming

Retiming moves registers across combinational logic, changing the sequential equivalence points.

**Without SVF/do file:** LEC fails because registers cannot be matched.
**With SVF/do file:** The tool uses the transformation record to remap registers.

```tcl
# SVF records retiming moves
# Formality reconstructs the equivalence mapping from SVF
set_svf retiming.svf
```

### Multibit Banking

Some synthesis tools merge multiple single-bit flip-flops into multi-bit cells for area/power optimization.

```tcl
# Formality handles multibit banking via SVF
# Ensure SVF is complete and accurate
```

### Black Boxing

For blocks that cannot be formally verified (analog, custom logic, hard macros):

```tcl
# In Formality
set_black_box r:/WORK/analog_block
set_black_box i:/WORK/analog_block

# In Conformal
add_black_box -module analog_block
```

### Datapath Optimization

Arithmetic optimizations (carry-save adders, Booth multipliers) restructure the logic significantly. SVF/do files guide the LEC tool through these transformations.

## Common Issues and Fixes

**Issue: Unmatched key points (registers cannot be mapped)**
- Check SVF/do file — if missing or incomplete, the tool cannot track register transformations.
- Verify that naming conventions are consistent between reference and implementation.
- Use name-based matching rules to help the tool match renamed registers.
- Check for hierarchy changes (ungrouping) that alter register paths.

**Issue: Non-equivalent points after synthesis**
- Verify that boundary optimization is disabled on blocks crossing verification boundaries.
- Check for retiming without corresponding SVF records.
- Inspect the failing logic cone — compare the Boolean function between reference and implementation.
- Ensure the correct library is loaded (mismatched library can cause false non-equivalences).

**Issue: Abort points (tool cannot prove equivalence)**
- Increase the verification effort/timeout.
- Simplify the problem by reducing the logic cone (set intermediate points as comparison points).
- Add constraints to eliminate unreachable states.
- Check for combinational loops.

**Issue: LEC fails on DFT-inserted design**
- Set scan_enable and scan_mode to their functional values (typically 0).
- Verify that test-only logic is properly constrained.
- Use the DFT tool's guidance file.

**Issue: LEC fails after PnR ECO**
- Write the ECO SVF/guidance file from the PnR tool.
- Verify incrementally: compare pre-ECO vs. post-ECO (not RTL vs. post-ECO).
- Check for unintended functional changes in the ECO.

## Best Practices

1. **Always generate and use SVF/do files** — they are essential for tracking synthesis transformations.
2. **Verify at every transformation stage** — RTL-to-synthesis, synthesis-to-DFT, DFT-to-PnR, PnR-to-ECO.
3. **Run LEC before committing any netlist change** — catching functional bugs early saves weeks.
4. **Disable boundary optimization** on verification boundaries if LEC is problematic.
5. **Constrain test ports** to functional mode values for functional equivalence checking.
6. **Use hierarchical verification** for large designs — verify blocks independently, then verify the top level.
7. **Track unmatched points** — they represent unchecked logic. Zero unmatched points is the target.
8. **Abort points need attention** — they are not failures, but they are not proven correct either. Investigate and resolve them.
9. **Version-control SVF files** alongside netlists — they are paired artifacts.
10. **Automate LEC** as part of the flow — it should run automatically after every synthesis, optimization, and ECO step.
