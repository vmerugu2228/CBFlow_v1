# Interrupt Systems: Controllers, Priority, Nesting, and MSI

## Overview

Interrupt systems are the nervous system of an SoC, enabling asynchronous event notification from peripherals to processors. A well-designed interrupt architecture is critical for system responsiveness, real-time performance, and power efficiency. Modern SoCs may manage hundreds of interrupt sources across multiple processors, security domains, and power domains. This guide covers interrupt controller design, priority schemes, nesting, message-signaled interrupts, and practical implementation considerations.

## Interrupt Fundamentals

### Edge vs. Level Detection

**Level-triggered interrupts:**
- Interrupt signal is asserted (held active) until the source condition is cleared
- The interrupt controller samples the level; as long as it is active, the interrupt is pending
- Advantage: cannot miss an interrupt (it remains asserted until serviced)
- Disadvantage: if the handler does not clear the source, the interrupt fires repeatedly
- Use case: most peripherals (UART RX full, DMA complete, timer expired)

**Edge-triggered interrupts:**
- Interrupt is detected on the transition (rising edge, falling edge, or both)
- The controller latches the edge and sets a pending bit
- Advantage: no need to clear the source before returning from handler
- Disadvantage: can miss interrupts if two edges arrive before the first is acknowledged
- Use case: external pins, wakeup events, pulse-type signals

**Best practice:** use level-triggered for most internal peripherals. Use edge-triggered only when the interrupt source is inherently pulsed or when level-triggered would cause spurious re-entry.

### Interrupt Flow

The typical interrupt handling sequence:

1. **Peripheral asserts interrupt**: signal goes active (level) or transitions (edge)
2. **Controller registers pending**: interrupt status bit is set in the controller
3. **Priority evaluation**: controller compares pending interrupts against current priority
4. **CPU notification**: controller asserts IRQ/FIQ to the processor if a higher-priority interrupt is pending
5. **CPU acknowledges**: processor reads the interrupt acknowledge register; controller returns the interrupt ID and raises the running priority
6. **Handler execution**: software dispatches to the appropriate interrupt service routine (ISR)
7. **End of interrupt (EOI)**: software writes the EOI register; controller lowers the running priority
8. **Source clear**: handler clears the interrupt condition at the peripheral (for level-triggered)

## Interrupt Controller Architectures

### Simple Interrupt Controller

Basic controllers for microcontrollers and small SoCs:

- **Status register**: one bit per interrupt source (read to see pending interrupts)
- **Enable/mask register**: per-bit enable/disable
- **Priority register**: fixed or configurable priority per source
- **No nesting**: flat priority, one interrupt at a time
- **Limitations**: no hardware priority, no nesting, software must poll status register

### ARM GIC (Generic Interrupt Controller)

The GIC is the standard interrupt controller for ARM-based SoCs:

**GIC Architecture Versions:**
- **GICv2**: supports up to 1020 interrupts, 8 CPU interfaces, 256 priority levels
- **GICv3**: scales to thousands of interrupts, affinity-based routing, system register access, LPI support
- **GICv4**: adds direct injection of virtual interrupts for virtualization

**GIC Components:**
- **Distributor**: manages interrupt sources, priority, target CPUs, enable/disable
- **CPU Interface**: per-CPU interface for acknowledge, EOI, priority mask, running priority
- **Redistributor (GICv3)**: per-CPU component managing SGIs, PPIs, and LPIs

**Interrupt Types:**
- **SGI (Software Generated Interrupt)**: IDs 0-15; generated by software write to a register; used for inter-processor communication (IPI)
- **PPI (Private Peripheral Interrupt)**: IDs 16-31; per-CPU private interrupts (timers, performance monitors)
- **SPI (Shared Peripheral Interrupt)**: IDs 32-1019; shared across CPUs; routed by distributor
- **LPI (Locality-specific Peripheral Interrupt)**: GICv3+; message-based interrupts; supports thousands of sources (MSI for PCIe)

### RISC-V PLIC (Platform-Level Interrupt Controller)

The PLIC is the standard external interrupt controller for RISC-V:

- **Sources**: up to 1023 external interrupt sources
- **Targets**: multiple harts (hardware threads), each with configurable priority threshold
- **Priority**: 7-bit priority per source
- **Claim/complete**: target claims pending interrupt (returns ID), completes when done
- **No nesting**: PLIC does not support hardware nesting; must be implemented in software if needed

RISC-V also defines CLIC (Core-Local Interrupt Controller) for faster, nested interrupt handling with hardware priority preemption.

### NVIC (Nested Vectored Interrupt Controller)

ARM Cortex-M processors use the NVIC, tightly coupled to the core:

- **Vectored**: hardware reads the ISR address from a vector table; no software dispatch overhead
- **Nested**: hardware stacking of registers enables interrupt preemption with minimal latency
- **Priority grouping**: configurable split between preemption priority and sub-priority
- **Tail chaining**: if a higher-priority interrupt arrives during ISR return, the CPU skips un-stacking and immediately enters the new ISR
- **Late arrival**: if a higher-priority interrupt arrives during stacking, the CPU switches to the higher-priority ISR without restarting stacking

## Priority and Preemption

### Priority Schemes

- **Fixed priority**: hardwired priority order; simplest but inflexible
- **Configurable priority**: software-programmed priority per source (GIC: 8-bit field, 256 levels)
- **Group priority**: GIC supports priority grouping; upper bits determine preemption, lower bits determine sub-priority within a group
- **Priority mask**: per-CPU mask suppresses interrupts below a threshold

### Preemption (Nesting)

Interrupt nesting allows a higher-priority interrupt to preempt a lower-priority handler:

**Hardware nesting (NVIC):**
1. CPU is executing ISR for interrupt A (priority 2)
2. Interrupt B arrives (priority 1, higher)
3. Hardware automatically stacks A's context and vectors to B's ISR
4. When B completes, hardware restores A's context and resumes A's ISR

**Software nesting (GIC):**
1. CPU acknowledges interrupt A (GIC raises running priority to A's level)
2. Software saves context and re-enables interrupts
3. Interrupt B arrives (higher priority than A's running priority)
4. CPU acknowledges B, GIC raises running priority
5. When B's ISR completes, EOI lowers running priority; A's ISR resumes

**Nesting risks:**
- Stack overflow: each nested interrupt consumes stack space
- Priority inversion: low-priority ISR holds a resource needed by high-priority ISR
- Increased worst-case latency analysis complexity

### Interrupt Latency

Factors contributing to interrupt latency:

- **Detection latency**: synchronizer stages for asynchronous interrupt sources (2-3 clock cycles)
- **Priority evaluation**: controller evaluates pending vs. running priority (1-2 cycles)
- **CPU pipeline flush**: processor flushes pipeline and stacks registers (12 cycles for Cortex-M, more for Cortex-A)
- **Vector fetch**: read ISR address from vector table (1-3 cycles depending on memory)
- **Handler prologue**: save additional registers, determine source (software overhead)

Cortex-M achieves 12-cycle interrupt latency from assertion to first ISR instruction. Cortex-A latency is higher (50-100+ cycles) due to deeper pipeline and more complex context save.

## Message-Signaled Interrupts (MSI)

### Concept

Instead of dedicated interrupt wires, MSI uses memory writes to signal interrupts:

- Device writes a specific data value to a specific memory address
- The write is decoded by an interrupt controller (GIC ITS for ARM, MSI controller for others)
- Controller translates the write into an internal interrupt

### Advantages Over Wire-Based Interrupts

- **Scalability**: no physical wires needed; thousands of MSI sources are practical
- **No sharing**: each device/function gets unique MSI vector(s)
- **Ordering**: MSI write is ordered with respect to preceding DMA writes, eliminating race conditions
- **Routing flexibility**: MSI target address determines CPU affinity

### MSI in PCIe

- **MSI**: device writes to a single address with varying data values (up to 32 vectors)
- **MSI-X**: table-based; each vector has independent address/data pair (up to 2048 vectors)
- **GIC ITS (Interrupt Translation Service)**: translates MSI writes into LPIs, routes to target CPUs

### MSI Implementation in SoC

- **MSI controller**: decodes memory-mapped writes within the MSI address range
- **Translation table**: maps (device ID, event ID) to (interrupt ID, target CPU)
- **Doorbell register**: the address that devices write to; typically in the interconnect or GIC ITS
- **Collateral**: each MSI-capable device needs configuration of MSI address and data in its PCIe capability structure

## Power Domain Considerations

### Interrupt Routing Across Power Domains

Interrupts must remain functional when parts of the SoC are powered down:

- **Always-on interrupt controller**: portion of the controller in the always-on power domain
- **Wake-up interrupts**: designated interrupts that can wake the system from deep sleep
- **Interrupt forwarding**: route wake-capable interrupts to the always-on domain while non-wake interrupts are masked during sleep
- **GIC wake request**: GIC signals a wake request to the power management unit when a pending interrupt exceeds the priority threshold

### Interrupt and Clock Gating

- Interrupt controller must remain clocked to detect incoming interrupts
- Some controllers support a low-power monitoring mode that only monitors wake-capable sources
- Clock gating of the full controller is possible only when no interrupts are pending

## Debug and Verification

### Common Interrupt Bugs

- **Missing interrupt clear**: handler does not clear the source; level-triggered interrupt re-fires continuously
- **Priority inversion**: critical interrupt cannot preempt because priority is misconfigured
- **Spurious interrupts**: interrupt source de-asserts before CPU acknowledges; GIC returns ID 1023 (spurious)
- **Interrupt storm**: malfunctioning peripheral generates continuous interrupts, starving the CPU
- **Race condition**: interrupt fires between enable and handler setup; handler is not ready

### Verification Strategy

- **Register access tests**: verify all controller registers are accessible and reset correctly
- **Priority verification**: generate simultaneous interrupts at different priorities; verify correct servicing order
- **Nesting tests**: verify nested interrupt preemption and proper context restoration
- **Edge case tests**: simultaneous assertion and clear, back-to-back interrupts, priority changes during handling
- **Power state transitions**: verify wake-up interrupts function across power state changes

### Interrupt Characterization

- **Measure worst-case latency**: inject interrupt at worst-case moment (during critical section, cache miss, bus contention)
- **Jitter measurement**: distribution of interrupt latency over many samples
- **Throughput**: maximum interrupt rate the system can sustain without dropping or starving

A robust interrupt architecture with proper priority assignment, nesting configuration, and power-domain awareness is fundamental to SoC functionality. Invest in thorough verification early, as interrupt bugs are among the most difficult to diagnose in silicon.
