# Serial Protocols: SPI, I2C, and UART

## Overview

SPI, I2C, and UART are the foundational low-speed serial protocols found in virtually every SoC. Despite being decades old, they remain essential for configuration, sensor communication, debug, and inter-chip control. Each protocol makes different trade-offs between pin count, speed, complexity, and multi-device support. Understanding their timing, modes, error handling, and hardware implementation is critical for robust SoC integration.

## SPI (Serial Peripheral Interface)

### Architecture

SPI is a synchronous, full-duplex, master-slave protocol using four signals:

- **SCLK**: serial clock, generated by master
- **MOSI (SDO)**: master-out slave-in data
- **MISO (SDI)**: master-in slave-out data
- **SS/CS**: slave select (active low), one per slave

The master provides the clock and selects the slave. Data is simultaneously transmitted (MOSI) and received (MISO) on every clock cycle, making SPI inherently full-duplex.

### SPI Modes (CPOL/CPHA)

SPI defines four modes based on clock polarity and phase:

| Mode | CPOL | CPHA | Behavior |
|---|---|---|---|
| 0 | 0 | 0 | Clock idle low, data captured on rising edge, shifted on falling |
| 1 | 0 | 1 | Clock idle low, data captured on falling edge, shifted on rising |
| 2 | 1 | 0 | Clock idle high, data captured on falling edge, shifted on rising |
| 3 | 1 | 1 | Clock idle high, data captured on rising edge, shifted on falling |

Mode 0 and Mode 3 are most common. The master and slave must agree on the mode; mismatch causes data corruption.

### SPI Timing

Key timing parameters:

- **SCLK frequency**: typically 1-100 MHz; limited by slave device capability and board trace length
- **Setup time (tSU)**: data must be stable before capture edge
- **Hold time (tHD)**: data must remain stable after capture edge
- **CS-to-SCLK delay**: minimum time between CS assertion and first SCLK edge
- **SCLK-to-CS release**: minimum time between last SCLK edge and CS de-assertion
- **Inter-frame gap**: some devices require minimum CS high time between transactions

### SPI Variants

- **Dual SPI**: MOSI and MISO used bidirectionally, doubling throughput (common in SPI flash)
- **Quad SPI (QSPI)**: four data lines (IO0-IO3), quadrupling throughput; standard for NOR flash (up to 400 Mbps)
- **Octal SPI (OSPI)**: eight data lines with DDR; up to 400 MHz x 8 bits x 2 = 6.4 Gbps
- **Multi-CS**: single master driving multiple CS lines for device selection

### SPI Hardware Implementation

An SPI controller in an SoC typically includes:

- **Shift register**: 8/16/32-bit configurable
- **TX/RX FIFOs**: buffered transfers reduce CPU interrupt frequency
- **Clock divider**: generates SCLK from system clock
- **DMA interface**: for high-throughput bulk transfers (flash read/write)
- **CS control**: hardware-managed CS with configurable timing, or software-controlled GPIO
- **Mode configuration**: CPOL, CPHA, bit order (MSB/LSB first), word size

### SPI Multi-Master

SPI does not natively support multi-master. Workarounds include:

- GPIO-based arbitration before driving SCLK/CS
- External arbitration logic
- Tri-state bus with collision detection (unreliable)

In practice, multi-master SPI is rare; I2C is preferred for multi-master scenarios.

## I2C (Inter-Integrated Circuit)

### Architecture

I2C is a synchronous, half-duplex, multi-master protocol using two signals:

- **SCL**: serial clock (open-drain with pull-up)
- **SDA**: serial data (open-drain with pull-up)

Open-drain signaling enables wired-AND: any device can pull the bus low. Pull-up resistors (typically 2.2K-10K ohm) return the bus to high when released. Multiple masters and slaves share the same two-wire bus.

### I2C Addressing

- **7-bit addressing**: 128 possible addresses; 16 reserved, leaving 112 usable
- **10-bit addressing**: extends to 1024 addresses; uses two-byte address header
- **General call**: address 0x00 broadcasts to all devices
- **Reserved addresses**: 0x00 (general call), 0x01-0x07 (CBUS, reserved), 0x78-0x7F (10-bit prefix, device ID)

### I2C Protocol

A typical I2C write transaction:

1. **START condition**: master pulls SDA low while SCL is high
2. **Address byte**: 7-bit slave address + R/W bit (0=write); MSB first
3. **ACK**: slave pulls SDA low on 9th clock to acknowledge
4. **Data bytes**: one or more bytes, each followed by ACK/NACK from receiver
5. **STOP condition**: master releases SDA while SCL is high

Read transactions use repeated START to switch direction without releasing the bus.

### I2C Speed Modes

| Mode | Speed | Pull-up |
|---|---|---|
| Standard | 100 kbps | 4.7K-10K ohm |
| Fast | 400 kbps | 1K-4.7K ohm |
| Fast-mode Plus | 1 Mbps | ~500 ohm |
| High-speed | 3.4 Mbps | Active pull-up |
| Ultra-fast | 5 Mbps | Push-pull (not open-drain) |

Higher speeds require lower pull-up resistance to charge bus capacitance faster. Bus capacitance should not exceed 400 pF for standard mode.

### I2C Multi-Master Arbitration

When multiple masters attempt simultaneous communication:

1. Both masters drive SDA while monitoring the bus
2. If a master drives SDA high but reads SDA low (another master is pulling it low), the first master loses arbitration
3. The losing master releases the bus and waits
4. Arbitration is non-destructive: the winning master's transaction continues uninterrupted

### I2C Clock Stretching

A slow slave can hold SCL low to pause the master:

- Slave pulls SCL low after ACK bit to request more time
- Master detects SCL is held low and waits
- Slave releases SCL when ready
- Clock stretching can cause timing unpredictability; some masters have timeout protection

### I2C Error Handling

- **NACK detection**: master detects NACK and can retry or abort
- **Bus stuck low**: SDA or SCL stuck low; master generates 9 SCL clocks to unstick, followed by STOP
- **Bus timeout**: SMBus defines a 35 ms timeout; if SCL is low longer, devices reset
- **Repeated START**: used to maintain bus ownership between write address and read data phases

### I2C Hardware Implementation

SoC I2C controller features:

- **Slave address register**: hardware comparison for fast address matching
- **TX/RX FIFOs**: reduce interrupt frequency
- **DMA support**: for bulk transfers (EEPROM programming)
- **SMBus compatibility**: timeout, PEC (Packet Error Check), alert response
- **Multi-address**: support multiple slave addresses for different register banks
- **Bus clear**: automatic 9-clock recovery sequence

## UART (Universal Asynchronous Receiver/Transmitter)

### Architecture

UART is an asynchronous, full-duplex, point-to-point protocol using two signals:

- **TX**: transmit data (idle high)
- **RX**: receive data
- Optional: **RTS/CTS** (hardware flow control), **DTR/DSR** (modem control)

No clock signal is shared; both sides must agree on the baud rate (bit rate) for successful communication.

### UART Frame Format

```
IDLE | START | D0 | D1 | D2 | D3 | D4 | D5 | D6 | D7 | [PARITY] | STOP | IDLE
```

- **Start bit**: always 0 (falling edge from idle high triggers receiver)
- **Data bits**: 5, 6, 7, or 8 bits; LSB first (8 bits most common)
- **Parity bit**: optional; even, odd, mark (always 1), space (always 0), or none
- **Stop bits**: 1, 1.5, or 2 stop bits (always high)

Common configuration: 8N1 (8 data bits, no parity, 1 stop bit) at 115200 baud.

### Baud Rate and Clock Recovery

The receiver samples each bit at 16x the baud rate:

1. Detect falling edge (start bit)
2. Wait 8 sample clocks (half a bit period) to reach center of start bit
3. Verify start bit is still low (reject noise glitches)
4. Sample each subsequent bit at 16-sample intervals (center of each bit)
5. Majority voting (3 or 5 samples around center) improves noise immunity

Baud rate accuracy is critical. Clock frequency mismatch between TX and RX accumulates over the frame. For 8N1 (10 bit times), the total drift at the last bit must be less than half a bit period, requiring clock accuracy better than 5% (typically < 2% in practice).

### Standard Baud Rates

9600, 19200, 38400, 57600, 115200, 230400, 460800, 921600, 1000000, 3000000

Higher baud rates (1-12 Mbps) are supported by some controllers but require careful board design and short trace lengths.

### UART Flow Control

**Hardware flow control (RTS/CTS):**
- Receiver de-asserts RTS when its buffer is nearly full
- Transmitter monitors CTS and pauses when de-asserted
- Prevents buffer overflow at the receiver

**Software flow control (XON/XOFF):**
- Receiver sends XOFF (0x13) character to pause transmitter
- Sends XON (0x11) to resume
- Cannot be used with binary data (data may contain 0x11/0x13)

### UART Error Detection

- **Framing error**: stop bit is not high; indicates baud rate mismatch or noise
- **Parity error**: computed parity does not match received parity bit
- **Overrun error**: new data arrives before previous data is read from receive buffer
- **Break condition**: RX held low for longer than one frame; intentional signal to reset communication

### UART Hardware Implementation

SoC UART controller (often 16550-compatible) features:

- **Baud rate generator**: configurable divider from system clock
- **TX/RX FIFOs**: 16-256 bytes; configurable trigger levels for interrupts
- **DMA support**: reduces CPU overhead for large data transfers
- **Auto-baud detection**: some controllers can detect baud rate from incoming start bit timing
- **IrDA mode**: modulated output for infrared communication
- **RS-485 mode**: half-duplex with automatic DE (driver enable) control
- **LIN mode**: Local Interconnect Network for automotive applications

## Protocol Selection Guide

| Criteria | SPI | I2C | UART |
|---|---|---|---|
| Speed | Highest (100+ MHz) | Moderate (3.4 MHz max) | Moderate (12 Mbps max) |
| Pin count | 3 + 1/slave | 2 (shared) | 2 (point-to-point) |
| Multi-device | CS per slave | Addressing | Point-to-point only |
| Multi-master | Not standard | Yes | N/A |
| Full duplex | Yes | No | Yes |
| Typical use | Flash, ADC, display | Sensors, PMIC, EEPROM | Debug console, GPS, BT |

Each protocol has its niche: SPI for high-speed peripheral data, I2C for multi-device configuration buses, and UART for simple debug and point-to-point communication. Most SoCs integrate multiple instances of all three.
